Things I agree with:
The core decisions are right — remove Rail 2/4, promote webhooks into onboarding, make sub-agent mode the primary pattern, and leave Messages/Guardrails/Approvals alone for now. The "don't unify guardrails yet" call is smart — no point redesigning the API surface in the skill file if the backend hasn't changed.
Things I'd refine or push back on:

Webhook promotion — "strongly recommended" might not be strong enough. Given that Rail 5 card delivery depends on either webhooks or polling bot messages, and the whole sub-agent lifecycle benefits from real-time events, I'd go further: make callback_url a required field in the registration example (even if the API technically still accepts it as optional). The skill file teaches behavior — if the example includes it, bots will include it. Then mention the bot messages fallback as a backup, not as a co-equal path.
The plan says "Add a dedicated section: How to Make a Transaction" — I think this should be the centerpiece of the document, not buried in the Rail 5 section. The whole point of this skill is enabling transactions. I'd put it right after onboarding as a prominent "Making a Purchase" section, then let Rail 5 and Stripe x402 be the implementation details underneath. The flow should read: "Here's how you buy something" → "Here's how Rail 5 works specifically" → "Here's how x402 works specifically."
The plan doesn't mention updating the heartbeat.md references. The live heartbeat.md still references Rail 2 and Rail 4 detail checks. Since the plan says "skill.md only," that's technically fine — but we should flag that heartbeat.md will be stale after this update and needs a follow-up pass.
ClawHub safety scanning — the plan doesn't explicitly address this. The existing security section is good, but with Rail 5 involving decryption keys and card data, I'd make sure the skill has very explicit language about the sub-agent's ephemeral nature, that decrypted card data must never be stored/logged/persisted, and that the key is single-use and server-issued. This isn't just good practice — it's what a safety scanner would look for. Language like "the sub-agent is deleted after checkout and all decrypted material is destroyed" should be prominent.
The GET /bot/status response example needs careful thought. When we strip Rail 2/4 from it, we should make sure the remaining response shape still makes sense. If a bot only has Rail 5 and maybe Stripe x402, the example should reflect that realistic configuration rather than showing every possible rail.

Overall verdict: The plan is about 90% there. I'd restructure slightly to make the transaction flow more central rather than Rail 5-specific, be more aggressive on webhook promotion, and add explicit safety language for the scanning concern. But the scope, the "leave these alone" decisions, and the removal list are all correct.
